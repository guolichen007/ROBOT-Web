# 多车辆命令路由设计（G2 预留；G1 不启用）

## 现状（只读审查结论，2026-11-12）

`services/command-dispatcher/main.py`：
- 单一 MQTT 客户端连接 **原 Broker**（settings.mqtt_host）；
- CANONICAL 车辆 → `robot/{vehicle_id}/command`（原 Broker）；
- VEHICLE_AGENT_V1 车辆 → `_platform/vehicle-agent-v1/{vehicle_id}/command`（原 Broker），
  由**原 vehicle-agent-adapter** 消费并下行；前置门：adapter_healthy + downlink 总开关 +
  allowlist + boot 绑定 + 过期校验（fail-closed）。

**风险（F 指出的问题）**：001 接入独立 Broker 后，若直接启用下行，dispatcher 的命令仍发往
原 Broker——原 adapter 虽然能收到，但 scope/绑定语义与专属 Adapter/Ingress 分离，
001 的命令将不会经过其专属传输路径，且与原 Broker 权限面耦合。
**不得把原生产 platform 凭证交给新 Broker 绕过该问题。**

## 目标设计（G2 实施；G1 仅冻结接口）

1. **按设备 Broker 路由**：dispatcher 按车辆 transport_profile 选择目标客户端。
   - 新增每设备 `transport_profile` 归属（接入 manifest 字段，落 DB 或车队配置）；
   - dispatcher 支持多 MQTT 客户端：`default`（原 Broker）与每个独立入口一个专用客户端
     （r001-broker 等），各自使用**该入口独立签发的内部账号**（非原生产 platform 凭证）；
   - 路由失败（未知 profile）→ 拒绝派发并记录审计，绝不回退到错误 Broker。
2. **专属下行面**：独立入口的专属 Adapter 继续消费其 Broker 的
   `_platform/vehicle-agent-v1/{vehicle}/command`；绑定/allowlist/过期校验沿用现有逻辑。
3. **G1 冻结状态**：downlink 总开关 false、allowlist 空、001 execution_profile=telemetry-only；
   任何命令路径保持 fail-closed，不提前启用。

## 验收口径（G2 启用时）

- 001 命令到达 8884 Broker（而非 8883）的包级证据；
- 错误路由反证：模拟 002/001 交叉派发均被拒绝；
- 原 Broker 上无 001 命令痕迹；原 platform 凭证不出原 Broker。
