# 仓库封板与发布流程

> 这是仓库封板（repository seal）与服务器发布（server release）的执行 SOP。两者是**两件事**，不要混在一起。

## 仓库封板（GitHub side）

```text
PHASE 0  工作区 / Git / gh auth 检查
PHASE 1  产品代码候选确认（APPLICATION_CODE_BASELINE）
PHASE 2  branch CI 全绿
PHASE 3  Field Release 软件 Gate（软件包/安装器，非真车验收）
PHASE 4  PR → main
PHASE 5  CodeQL / Dependency Review 全绿
PHASE 6  main ff-only 合并
PHASE 7  main post-merge CI
PHASE 8  创建 repository consolidated tag
PHASE 9  关闭 stale Dependabot PR
PHASE 10 删除已 fully-merged 历史支线
PHASE 11 main 分支保护
PHASE 12 最终库存检查
```

关键约束：

- 只允许 `main` 长期分支；临时分支合入即删。
- 删除分支前必须 `git merge-base --is-ancestor` 返回 0。
- 禁止 force push / rebase 已发布历史 / 删除 tag / reset 抹历史。

## 服务器发布（Server side，GitHub merge 不自动触发）

服务器发布是独立授权流程，需要 Owner 明确授权：

```text
exact 40 位 SHA
  → preflight
  → backup（非空 + gzip -t + sha256 一致 + 0600）
  → deploy（all-app）
  → verify（5 core healthy + OCI revision == SHA + DB revision 不变）
  → rollback rehearsal（A→B→A→B，最终停在 B）
  → 生产浏览器只读验收（TLS / login / Monitor / 无 runtime fatal）
```

```text
APPLICATION_CODE_BASELINE = 4fd3e59d39190b6fab0688aa01e80f1e4cca4a86
SERVER_RUNTIME_SHA        = 584efcfda60b8d39c516a9939bc0481609fc6f3c

```

## 禁止

- 把「仓库 merge」当作「服务器已部署」。
- 把「软件 E2E PASS」当作「实车现场验收 PASS」。
- 把「服务器已部署」当作「正式产品 Release」。
- 在 field acceptance PENDING 时创建正式 Release tag。
